The Cisco 9800 TAG Architecture

Every AP joined to a Cisco 9800 WLC is assigned exactly three tags. Tags are pointers — they reference Profiles which contain the actual configuration. This separation makes large-scale changes efficient: update one profile and every AP using that tag inherits the change instantly.

The Three Tags — Mental Model

Think of tags as personality slots on each AP. When an AP joins, the WLC checks which tags are assigned and loads the referenced configuration:

AP joins WLC
│ ├─ Policy Tag -> Policy Profile (VLAN, switching mode, QoS, ACL) │ -> WLAN Profile(s) (which SSIDs to broadcast) │ ├─ Site Tag -> AP Join Profile (NTP, syslog, CAPWAP timers) │ -> Flex Profile (if present -> FlexConnect mode) │ └─ RF Tag -> RF Profile 2.4G (channel, power, DCA for 2.4 GHz) -> RF Profile 5G (channel, power, DCA for 5 GHz) -> RF Profile 6G (channel, power, DCA for 6 GHz)
ℹ️Key Rule: One AP = exactly one Policy Tag + one Site Tag + one RF Tag. You cannot assign multiple tags of the same type to a single AP.
✅Tags and profiles are created independently. One profile can be referenced by many tags — change the profile once and all APs using it update immediately.
🏷️

Policy Tag — Deep Dive

Purpose

The Policy Tag answers: Which SSIDs does this AP broadcast, and what happens to clients on each SSID? It is a mapping table: each row pairs a WLAN Profile (SSID definition) with a Policy Profile (client behavior).

Policy Tag: Tag-HQ-Floor2
WLAN Profile -> Policy Profile ───────────────────────────────────────── Corp-WiFi6 -> Policy-Corp (VLAN 10, Central, 802.1X) Guest-WiFi -> Policy-Guest (VLAN 200, Central, Web Auth) IoT-Sensors -> Policy-IoT (VLAN 300, Local Switch, PSK) ↑ up to 16 WLAN-Policy pairs per tag

Key Constraints

  • Maximum 16 WLAN-Policy mappings per Policy Tag
  • One AP can have only one Policy Tag — choose mappings carefully
  • The same WLAN Profile can appear in multiple Policy Tags (with different Policy Profiles) to serve different floors/sites differently
  • Removing a WLAN from a Policy Tag immediately stops that SSID on all APs with that tag — no grace period

Site Tag — Deep Dive

Purpose

The Site Tag controls how the AP operates — its mode (Local or FlexConnect) and its management settings. It references two profiles:

  • AP Join Profile — always required. Controls NTP, syslog, CAPWAP timers, SSH access, statistics interval.
  • Flex Profile — optional. Its presence is what puts the AP into FlexConnect mode.
Site Tag Decision Logic
Site Tag has Flex Profile? │ ├── NO -> AP operates in Local Mode │ All client data tunneled via CAPWAP to WLC │ VLAN assignment: WLC-side (Policy Profile VLAN) │ └── YES -> AP operates in FlexConnect Mode Client data can be switched locally at the AP VLAN assignment: Flex Profile VLAN override (branch VLAN) AP survives WAN outage in standalone mode

"Enable Local Site" Checkbox

  • Checked (default) — APs are directly/locally connected to the WLC. Data keepalive and CAPWAP control traffic behave as if WLC is close.
  • Unchecked — APs are at a remote site (branch over WAN). Combined with a Flex Profile = FlexConnect remote-branch deployment.
🚨Adding or removing a Flex Profile from a live Site Tag causes all APs using that tag to change operating modes. This triggers a brief client disconnect (~5–10 seconds) as radios reset.
Configuration › Tags & Profiles › Tags › Site

RF Tag — Deep Dive

Purpose

The RF Tag controls radio behavior — channel selection, transmit power, channel width, and Wi-Fi generation settings per band. It references up to three RF Profiles: one per band (2.4 GHz, 5 GHz, 6 GHz).

RF Tag: Tag-RF-Enterprise
Band -> RF Profile Key Settings ────────────────────────────────────────────────── 2.4 GHz -> RF-2.4-Corp Ch 1/6/11, 20 MHz, TPC enabled 5 GHz -> RF-5-Corp Ch 36-64, 80 MHz, DCA, TPC 6 GHz -> RF-6-Corp Ch 1-93, 80/160 MHz (6E APs) Different floor types can use different RF Tags for density tuning
ℹ️You can use the same RF Profile for 2.4 GHz and 5 GHz, or create separate profiles for fine-grained control. A common practice is one RF Tag per 'zone type' (e.g., open office, conference room, warehouse).

TAG Assignment Methods

Tags can be assigned to APs using three different methods, from most specific to least specific:

Method 1 — Static (per AP MAC)

Navigate to Configuration › Wireless › Access Points, click the AP, and manually set each tag. This is the most explicit method and overrides everything else.

Configuration › Wireless › Access Points › <AP Name> › General Tab › Tags

Method 2 — Dynamic via RADIUS VSA

The RADIUS server can push tag assignments in the Access-Accept message using Cisco AVPair attributes. This allows different users/devices to trigger different AP tag configurations dynamically — useful for multi-tenant or context-aware deployments.

RADIUS Access-Accept includes: Cisco-AVPair = "policy-tag=Tag-Corp" Cisco-AVPair = "site-tag=Tag-Site-HQ" Cisco-AVPair = "rf-tag=Tag-RF-High-Density"

Method 3 — Filter Rules (AP Filters)

Create rules based on AP name, AP model, or location to automatically assign tags when APs join. Navigate to Configuration › Wireless › Advanced › AP Filter.

ℹ️Priority: Static assignment > Dynamic RADIUS > Filter rules > Default tags. Static assignment always wins.
⚠️

The Default Tags Trap

The 9800 ships with three default tags pre-configured. Any AP that joins without an explicit tag assignment uses these defaults. This is convenient in a lab but dangerous in production.

DANGER SCENARIO: Engineer adds WLAN "Corp-WiFi6" to default-policy-tag to test on one AP. Result: EVERY AP in the network (200+ APs) that hasn't been explicitly tagged now broadcasts "Corp-WiFi6" — including APs in the parking lot, reception, conference rooms, and all branches. This is not a hypothetical — it has happened in production networks.
🚨Production Best Practice: Immediately after deployment, assign custom tags to all APs. Never use default-policy-tag for production SSIDs. Use default tags only as a safety net for untagged/new APs with no SSIDs (empty WLAN list).
✅Recommended approach: Create a 'quarantine' Policy Tag with no WLANs mapped. Assign this to unmanaged APs so they join but broadcast nothing until explicitly configured.
🔄

The Policy Tag is the closest equivalent to the AireOS AP Group — it defines which SSIDs an AP broadcasts. However, the AireOS AP Group settings are now distributed across all three C9800 tags:

⚠️CAPWAP restart behavior: Changing the tag assigned to an AP triggers a CAPWAP restart (~20–25 sec downtime). Changing a setting within an already-assigned profile does NOT cause a CAPWAP disconnect — the change takes effect immediately.

AP Tag Persistency (Release 17.6+)

Starting with IOS-XE 17.6, configured tags are automatically saved on the AP. This is critical for N+1 HA failover and AP migration between controllers — the AP carries its tag assignment with it.

Enable tag persistency globally (17.6+):
C9800(config)#ap tag persistency enable Before 17.6 — save tags to AP manually (per AP): c9800-1#ap name <APname> write tag-config (Available in GUI per-AP from release 17.4.1) Check tag assignments and source: C9800#show ap tag summary Validate all tag/profile configurations: C9800#wireless config validate

Moving APs Between Controllers — What to Expect

  • AP holds no tag info AND no mapping on new WLC → AP gets default tags (may broadcast wrong/no SSIDs)
  • Both WLCs have identical AP-to-tag mapping (static, location, or filter) → tags are preserved
  • Tags are saved on the AP and the tags exist on the new controller with no higher-priority override → tags are preserved
  • Tags saved on AP but the tags don't exist on new controller → AP falls back to default tags
  • Tag name matches but profile settings differ → AP operates with the new controller's profile settings
ℹ️This applies to APs moving from primary to secondary controller during N+1 redundancy failover. Pre-configure matching tag mappings on both controllers, or use tag persistency to avoid SSID disruption.

WNCd Architecture & Site Tag Design (Local Mode APs)

The C9800 runs a multiprocess architecture. The process responsible for AP and client sessions is the Wireless Network Controller daemon (WNCd). The number of WNCd instances determines parallelism — and site tag assignment determines which WNCd manages each AP.

C9800#show processes platform | include wncd
⚠️default-site-tag distributes APs round-robin across all WNCd processes. When clients roam between APs on different WNCds, interprocess communication is required — functional, but not optimal for performance or fast roaming.
✅Recommendation: Use custom named site tags. APs in the same site tag land on the same WNCd → all roaming is intra-WNCd (intraprocess) → lower latency, less CPU overhead, and better fast-roaming support.

Site Tag Design Recommendations (Local Mode)

  1. Use custom site tags — avoid default-site-tag when roaming or fast roaming is required
  2. Assign all APs in the same roaming domain to the same site tag
  3. Target ~500 APs per site tag for best performance (applies to all C9800 form factors)
  4. Do not exceed the platform-specific maximums in the table below
  5. In high-density deployments, use the platform-recommended number of site tags and distribute APs evenly

Roaming Between Policy Tags — wireless client vlan-persistent

The Problem: Slow Roam Across Different Policy Profiles

When a client roams between two APs where the same SSID is mapped to different Policy Profile names, the C9800 triggers a full reauthentication by design — the controller wants to re-evaluate the client's policy before allowing access. The side effect is a 2–5 second connectivity gap that breaks VoIP calls and interrupts TCP sessions.

WITHOUT vlan-persistent — slow roam (full reauthentication): Building A APs → Policy Tag A → Corp SSID → Policy-Corp-BldgA (VLAN 10) Building B APs → Policy Tag B → Corp SSID → Policy-Corp-BldgB (VLAN 20) Client roams Bldg-A → Bldg-B: 1. 802.11 reassociation 2. Full 802.1X EAP exchange ← 2–5 seconds, RADIUS round-trip 3. New DHCP lease ← client gets new IP on VLAN 20 4. TCP sessions broken ← VoIP call drops, SSH disconnects 5. New policy profile applied WITH vlan-persistent — seamless roam: Same policy tag / profile setup as above Client roams Bldg-A → Bldg-B: 1. 802.11 reassociation 2. WLC compares policy profiles ← only VLAN differs → allowed 3. Client KEEPS original IP on VLAN 10 4. Target profile ACL applied immediately 5. TCP sessions survive ← VoIP call continues
ℹ️Slow roam is by design when policy profiles fundamentally differ. wireless client vlan-persistent only bypasses reauthentication when the difference is in allowed attributes (VLAN, ACL, etc.). It does not suppress reauthentication when security parameters change.

How wireless client vlan-persistent Works Internally

At roam time the WLC performs a policy profile compatibility check between the source and target profiles:

  1. Client sends 802.11 Reassociation Request to the new AP
  2. C9800 identifies the target AP's Policy Tag → Policy Profile
  3. WLC compares source and target policy profiles attribute by attribute
  4. If only allowed-to-differ attributes differ → seamless migration (PMK reused, no new EAP)
  5. The client retains its original VLAN and IP address — "persistent VLAN"
  6. New ACLs from the target profile are applied to the client session immediately
ℹ️The feature name says "vlan" but VLAN is just the most common use case. ACL-only differences (same VLAN, different ACL) also benefit from this feature — client has no connectivity gap while the new ACL takes effect.

Attributes That CAN Differ — Seamless Roam Allowed

FlexConnect Site Tag Design Guidelines

For FlexConnect deployments, the Site Tag defines the fast-roaming domain — client keys (PMK cache) are distributed only among APs within the same Flex site tag.

RuleDetail
Never use default-site-tag for FlexClient keys are NOT distributed among APs in default-site-tag. 802.11r, CCKM, and OKC fast roaming will not work. Always use custom named site tags.
One site tag per physical locationDon't share a site tag across multiple geographically separate branches. Cross-branch key distribution wastes AP memory for clients that will never roam there.
AP limit per Flex site tagMax 100 APs per site tag for seamless fast roaming (extended to 300 with release 17.8). Roaming across Flex site tags = full client reauthentication.
Unique site tag names per branchRequired for overlapping IP address support across FlexConnect sites. Same site tag name = same roaming domain in the controller's view.

Overlapping IP Address Support (Release 17.3.3+)

C9800 supports clients with the same IP address at different branch locations when:

  • Policy profile is configured for FlexConnect local switching
  • Each branch location uses its own unique named site tag
⚠️Overlapping IP addresses are NOT supported for centrally switched policy profiles — regardless of AP mode (local or FlexConnect).

Mixed Campus + Branch Deployment

When a single deployment combines a campus (local-mode APs) with many small branches (FlexConnect APs), site tag design constraints conflict:

  • Campus (local mode): few large site tags (~500 APs each, aligned to WNCd count)
  • Branches (FlexConnect): many small site tags (one per branch, often only 5–20 APs each)
✅Best practice for mixed deployments: Use two separate WLC instances — one dedicated to campus APs (optimized for large site tags) and one for all branches, potentially a C9800-CL to optimize licensing cost.

Example 2 — FlexConnect Local Switching for a Remote Branch

FlexConnect

Use case: Remote branch office connected to HQ via WAN (MPLS or SD-WAN). Client traffic should NOT traverse the WAN — it must be switched locally at the branch to keep latency low and WAN bandwidth free.

Traffic Flow — FlexConnect Local Switching
Branch Site HQ / WLC ───────────────── ──────────────── [Client] ──802.11──> [AP] [WLC] │ ◄──── CAPWAP Control only ───► │ (no data traffic on WAN) │ [Branch Switch] │ VLAN 100 (local) │ [Branch Router] ──> Internet (local breakout) Only CAPWAP control packets cross the WAN — data stays local

Required configuration:

Field / SettingDescription
WLAN ProfileCorp-WiFi6 | WPA2-PSK or 802.1X
Flex ProfileFlex-Branch | VLAN override: Corp-WiFi6 -> VLAN 100 (branch local VLAN)
Policy ProfilePolicy-Corp | Central Switching: OFF | Local Switching: ON | Local DHCP: ON
Site TagTag-Site-Branch | AP Join Profile: APJoin-Branch | Flex Profile: Flex-Branch | Local Site: ✗
✅WAN failover: if the WAN link fails, connected clients remain on the network. The AP enters standalone mode and continues local switching. New client auth uses cached credentials (up to 100 MACs) or local RADIUS.
⚠️The VLAN number in the Flex Profile VLAN override does NOT need to match the WLC-side VLAN. Branch VLAN 100 is completely independent of the central VLAN 10 at HQ.

Example 6 — The Default Tag Trap (What Goes Wrong)

DANGER

Scenario: An engineer adds a new SSID to the default-policy-tag to quickly test it on one AP, not realizing the implications.

Before (safe): default-policy-tag -> empty (no WLANs mapped) 200 APs use default-policy-tag -> no SSIDs broadcast ✓ Engineer adds test WLAN: default-policy-tag -> TestSSID -> Policy-Test Result (unintended): ALL 200 APs now broadcast "TestSSID" including: • Parking lot APs • Reception APs • Executive floor • Remote branches • Conference rooms • Server room APs Immediate security exposure — unauthorized access point on every AP
🚨Never add production or test WLANs to the default-policy-tag unless you explicitly want ALL untagged APs to broadcast that SSID.
✅Fix: Create a custom Policy Tag for testing with only the specific test APs assigned to it. Keep default-policy-tag empty (or with a dead-end Policy Profile that has no VLAN).

Example 10 — Zone-Based ACL Enforcement with wireless client vlan-persistent

vlan-persistent

Use case: A manufacturing company runs a single CorpWiFi SSID (WPA2-Enterprise) across three distinct zones in the same facility. All zones use VLAN 50 — but each zone has different ACL restrictions for compliance and safety. Staff and engineers move between zones frequently and need seamless connectivity on their tablets and handheld scanners.

Zone Design

Zone layout — same VLAN, different ACLs
Zone: Open Office → Policy-Corp-Office → VLAN 50, no ACL Full corporate network access Zone: Production Floor → Policy-Corp-ProdFloor → VLAN 50, PROD-RESTRICT-ACL Blocks: HR servers (10.0.50.0/24), Finance (10.0.60.0/24) Allows: Production systems, Internet Zone: Receiving Dock → Policy-Corp-Dock → VLAN 50, DOCK-ACL Allows: WMS server (10.100.10.5) only Blocks: everything else All zones: same SSID "CorpWiFi", same 802.1X auth, same VLAN 50, same WLC

Without vlan-persistent — The Operational Problem

Engineer walks: Open Office → Production Floor Handheld scanner on 10.50.0.44 / VLAN 50, WMS query in progress Scanner associates to Production Floor AP └─ Policy profile name changed: Office ≠ ProdFloor → slow roam triggered ① Full 802.1X exchange (~2 seconds, scanner freezes) ② DHCP — gets same VLAN 50 (may renew same IP or get new one) ③ WMS query session terminated ✗ ④ Barcode scan lost ✗ ⑤ PROD-RESTRICT-ACL eventually applied Engineers report: "scanner drops every time we step on the floor"

With vlan-persistent — Seamless ACL Enforcement

Same walk: Open Office → Production Floor C9800 compares Policy-Corp-Office vs Policy-Corp-ProdFloor: VLAN: both 50 ← identical, no issue ACL: different ← allowed-to-differ attribute Seamless migration: ① PMK reused ← no 802.1X exchange ② Client retains IP: 10.50.0.44 ③ PROD-RESTRICT-ACL applied immediately ← ACL enforcement still works! ④ WMS session continues ✓ ⑤ Barcode scan uninterrupted ✓
